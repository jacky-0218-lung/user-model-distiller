  - 來源:https://developers.openai.com/codex/changelog

### 方向 B — 競品與類似工具（memory / personalization）

- mem0《State of AI Agent Memory 2026》:記憶層已成一級架構元件（LoCoMo/LongMemEval/BEAM 基準成形),但報告明言「**隱私與同意架構仍未解決**」（誰能檢視、留存多久、如何刪除,仍全靠應用層自理）——這正是本 repo 的核心賣點所在,方向持續正確。可借鏡處:報告建議「**核准狀態作為可查詢的中繼資料屬性**」（本 repo 已具備:`status` + digest-bound `approval`）與「行為人歸因:使用者陳述 vs 代理推斷」（本 repo 以 provenance `role`/`direct` 落實）。無新缺口。
  - 來源:https://mem0.ai/blog/state-of-ai-agent-memory-2026
- OpenMemory MCP 模式（同報告引述):local-first 儲存＋可瀏覽管理的 dashboard。本 repo 的等價物是「可審查的 JSON profile＋`compile` 預覽」;若日後使用者回報「檢視不便」,可考慮輕量唯讀 HTML 檢視器,暫列觀察不動手。

### 方向 C — 安全與隱私強化

- arXiv 2606.24322《Securing LLM-Agent Long-Term Memory Against Poisoning: Non-Malleable, Origin-Bound Authority with Machine-Checked Guarantees》(2026-06):形式化論證**寫入時來源綁定（write-time origin binding）是必要條件**——內容偵測與衍生歷史「both signals are malleable」,攻擊者可透過代理自我摘要、信任工具迴聲、人工佐證把不可信內容「洗白」。對照本 repo:evidence 在寫入時即綁定 provenance(`role=user`+`direct=true`),候選晉升需 digest-bound 人工核准,正是該文主張的 origin-bound + gated-elevation 結構,且我們的閘門是「人」而非可被 Sybil 攻擊的多方驗證。**定位第三度獲獨立研究印證,無新缺口**。
  - 來源:https://arxiv.org/abs/2606.24322
- 補充掃描:arXiv 2601.05504(memory poisoning 攻防)、MemPoison 等 2026 文獻的攻擊面(檢索污染、跨會話持久化)都以「自動寫入的記憶系統」為前提,本 repo 無自動寫入路徑,不在攻擊面內。
  - 來源:https://arxiv.org/abs/2601.05504

### 方向 D — 文件與易用性
