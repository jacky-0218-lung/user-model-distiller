### 方向 B — 競品與類似工具（memory / personalization）

- **arXiv 2608.10319《Do Personalized Skills Help Coding Agents?》**（本週最重要的獨立證據）：以 13 位開發者、206 個真實 session 做重放評估，發現「個人化 skill 相對無 skill 基線只有小而不一致的改善」，**但當偏好在歷史中反覆出現、且有多個相關例證時，個人化 skill 明顯有效**。這精確對應本 repo 的既有設計：confidence 0.9 給「跨 session 重複修正」、SKILL.md 明定「一次性任務要求視為情境脈絡，不是全域偏好」、`add-candidate` 支援多個 `--message-id` 合併佐證。**結論：recurrence-first 的設計方向獲得實證支持，無需改動**；若日後要調整，方向是更嚴而非更鬆（例如提高單一佐證候選的審查門檻）。
  - 來源：https://arxiv.org/abs/2608.10319
- 市場掃描（vectorize、Braintrust 的 2026 agent memory 工具盤點）：主流仍是自動寫入的 hosted memory 層，local-first + 人工核准的定位持續是差異點，未見結構可借鏡的新工具。
  - 來源：https://vectorize.io/articles/best-ai-agent-memory-systems 、https://www.braintrust.dev/articles/best-ai-agent-memory-tools-2026

### 方向 C — 安全與隱私強化

- arXiv 2606.04329《From Untrusted Input to Trusted Memory: A Systematic Study of Memory Poisoning Attacks in LLM Agents》：歸納六類 memory poisoning 攻擊、四個寫入通道；核心發現是「**寫入與檢索越積極的 agent 越容易被利用**」，且既有 prompt injection 防禦覆蓋不了 memory poisoning。本 repo 無自動寫入通道、晉升需 digest-bound 人工核准，不在其攻擊面內——定位再次獲印證。
  - 來源：https://arxiv.org/abs/2606.04329
- **openai/codex#24948（open bug，本週主要行動依據）**：Codex rollout session 檔因反覆累積的 `compacted.replacement_history` 與未截斷工具輸出，實際膨脹到 **700MB–2GB**（實例：732MB / 170,415 筆記錄，其中 compaction 佔 337.8MB、原始工具輸出佔 230.8MB；單筆記錄最大約 2.1MB）。對本 repo 的兩個影響：(1) 舊實作把整個 `.jsonl` 讀進記憶體再 decode + splitlines，峰值記憶體約為檔案大小的 3–4 倍，使用者若調高 `--max-total-mb` 去餵真實大檔就可能 OOM;(2) 超限錯誤訊息沒有任何補救指引。本週已修（見第 4 節）。另確認：`compacted` 記錄無 `role` 欄位，本來就會被解析器略過，**不存在 replacement_history 內容被重複計入證據的風險**（本週新增測試固定此行為）。
  - 來源：https://github.com/openai/codex/issues/24948

### 方向 D — 文件與易用性

- 落實上週佇列第 5 項：`evaluate_detector.py` 的 subcommand help 首字母小寫，與其他六個腳本不一致，本週已一致化。

## 4. 本週實際改動與驗收

### 主項：`normalize_sessions.py` 的 `.jsonl` 輸入改為串流解析（內部版本 0.4.0 → 0.4.1）

- **動機**：openai/codex#24948（見第 2 節方向 C）。
- **做法**：新增 `hash_file_bounded()`（1MB 區塊串流計算 SHA-256，邊讀邊強制大小上限，涵蓋 BOM 在內的原始位元組，與舊 `sha256_bytes(全檔)` 結果相同）與 `iter_jsonl_lines()`（逐實體行讀取後再以 `str.splitlines()` 細分，使邏輯行邊界——包括 U+2028/U+2029 等分隔字元——與舊的整檔 `splitlines()` 行為完全一致）。`parse_file` 的 `.jsonl` 路徑改走「先串流雜湊、再逐行解析」兩段式；原 `parse_codex_jsonl(bytes)` 保留為薄包裝（ZIP 路徑與既有呼叫者不受影響），核心邏輯移入 `parse_codex_jsonl_lines(lines)`。
- **效果**：峰值記憶體從「檔案大小的 3–4 倍」降到「單一最長行」等級；輸出逐位元組不變。
- **附帶修正**：(1) 超限錯誤訊息現在說明 Codex 大檔成因與補救方式（挑單一 session 檔或調高 `--max-total-mb`）；(2) 無效 UTF-8 改回報 `NormalizationError` 而非未捕捉的 traceback。
- **新增測試三個**：串流路徑與舊記憶體路徑輸出完全一致（含 BOM 雜湊、blank line、`compacted` 記錄不產生證據）；超限錯誤含補救指引；無效 UTF-8 fail closed。
