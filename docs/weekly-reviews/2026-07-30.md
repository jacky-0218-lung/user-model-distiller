## 4. 本週實際改動與驗收

### 改動 1：README 中英雙語「疑難排解」段落

於「私有工作流程／Private workflow」與「安全模型／Security model」之間各插入一節，涵蓋六種實際情境，內容全部對照程式碼行為撰寫：

1. 找不到 Python 或版本太舊（Windows `py -3`、Codex 內建 workspace Python；明確警告不要讓 agent 以重新實作腳本的方式繞過安全檢查——此警告與 SKILL.md 第 3 節既有語句一致）。
2. Skill 安裝後未觸發（開新 session、依「手動安裝」查另一個目錄、確認未多包一層目錄）。
3. `privacy_blocked`（exit 3）：說明這是依設計阻擋；只看聚合 `privacy-report.json`、不開被擋內容；處置方向與「必須重跑到新輸出目錄」。
4. `error: ...`（exit 2）：列出會被拒絕的路徑型態（已存在、位於 repo 樹、重疊、symlink、雲端同步），說明拒絕是刻意的。
5. `verify` 失敗（如 `Artifact hash mismatch`）：視為不可信、不要手動修補、重跑而非復原。
6. 外部審查資料包 `blocked`：說明此時不會產生任何 pack/mapping 檔，改用本機模型或人工審查，不要手工組揭露副本。

每一條的立場一致：**解釋「為什麼被擋是對的」再給出安全的下一步**，而不是教使用者繞過。未改動任何既有段落（`git diff` 確認純插入，28 行）。

### 改動 2：SKILL.md 第 8 節規則挑選指引

原文只說「use a compact core plus at most three to five task-relevant rules」，未定義「task-relevant」如何挑選，實務上 agent 會退回語意相似度。補上兩句：先取 scope 與當前 project／task／temporary 情境相符者，再取 `category` 與工作類型相符的全域規則（範例用 schema 實際允許的 `response_style`、`coding`，經 `ALLOWED_CATEGORIES` 核對）；並明確警告不要只依語意相似度——措辭與任務不同的規則仍可能是適用的那條。依據為方向 B 中 Mem0／Hindsight 的多訊號檢索共識。SKILL.md 維持 200 行。

### 改動 3：`skill_bundle.py` receipt 加入隱形字元掃描

上週補上了「正規化不受信任 transcript」與「CI 守門本 repo 追蹤檔案」兩層，但**高保證安裝路徑本身仍有缺口**：canonical bundle digest 只能證明「核准後位元組沒被改動」，無法證明「核准前人類看到的就是全部內容」。若暫存目錄中的檔案夾帶隱形指令，既有流程會照常算出 digest、照常產生 Approval receipt，審查者也看不出異常。

- 新增 `scan_invisible_characters()`：走訪 bundle 內所有檔案，UTF-8 檔案逐一掃描，非 UTF-8 檔案單獨計數並跳過文字掃描。
- `build_receipt()` 在計算 digest 前先掃描：**掃到即拒絕產生 receipt**（`BundleError`，訊息含檔名與碼位，但不回吐該字元本身）。通過時把 `{"status": "clean", "text_files": N, "non_text_files": M}` 寫入 receipt。
- `verify` 子命令同樣回報該欄位，讓舊 receipt 的驗證也能取得這項聲明。
- receipt `schema_version` 1.0 → 1.1；`install.md` 的 Approval receipt 必列項目同步新增此欄位，並說明「digest 證明位元組未變、不證明審查者看得到」的理由。
- 字元類別與 `normalize_sessions` 完全一致，並把既有的三層一致性測試擴充為**四層**，避免日後定義漂移。U+200C／U+200D 依既定理由保留。

### 改動 4：`profile-schema.md` 時間有效性語意

原本四個時間欄位只出現在範例 JSON 中，沒有任何一處定義它們各自代表什麼事件，實務上容易被混用（最常見的誤用是把 root `updated_at` 當成某條規則的變更時間）。新增「Temporal semantics」一節：

- 逐欄定義：`first_observed`／`last_observed` 是**證據觀察窗**；`approval.approved_at` 是**開始可被編譯的時刻**；`expires_at` 是**失效界線且為排他**（程式為 `expiry <= now` 即排除）；root `updated_at` 只是檔案 metadata。
- 說明如何還原「某時點適用哪條規則」：走 supersedes 鏈，取自身 `approved_at <= T` 且其替代者（若有）approved 於 T 之後者。並說明**為何刻意不新增 `superseded_at`**（同一事件的第二個時間來源可能與其來源的核准時間不一致）。附帶指出 `set-status superseded`（無替代者）會讓該次退場失去可還原的時間點，故應優先使用 `add-candidate --supersedes`。
- 明確 `--as-of` **只重算到期**，不還原歷史狀態：今天已 superseded／rejected 的規則，即使 `--as-of` 早於該變更也不會回到編譯結果中。這是刻意的限制，`--as-of` 不可當稽核工具用。
- staleness 立場：以審查處理，不做時間衰減；不得因時間流逝自行降級或移除使用者核准過的規則。
- **誠實記錄現況限制**：編譯支援 `expires_at`，但目前沒有任何指令會設定它（已列入下週佇列）。
- 新增 1 項測試，把「`--as-of` 只影響到期」由文件承諾變成**強制契約**：核准 → 編譯（規則在）→ `set-status superseded` → 以 2000 年為 `--as-of` 重新編譯（規則仍不在）。若日後有人讓 `--as-of` 連狀態一起回溯，這項測試會失敗。
- 檔案因此達 110 行，依 Skill 撰寫建議補上目錄（佇列第 7 項）。

### 4.2 對抗式覆審與修補

改動完成後，另以獨立的覆審流程對整份 diff 做對抗式檢查（指示為「只回報能以程式碼或實測確認的缺陷」）。覆審找出 7 項，其中 6 項確認為真並已修補，全部在同一個 PR 內完成：

1. **只掃內容、不掃檔名（真缺陷）**：`invisible_character_scan` 原本只檢查檔案內容。但檔名同樣被 digest 涵蓋，而且**檔名才是使用者在 receipt 上實際讀到的東西**：`notes<U+E0041>.md` 會渲染成 `notes.md`，與真正的 `notes.md` 無法分辨。已改為檔名與內容都掃，並在錯誤訊息中把該字元換成 `<U+XXXX>` 再輸出。
2. **掃描與 digest 未綁定（真缺陷）**：原實作走訪兩次、讀檔兩次，兩次之間檔案可被抽換，使用者可能核准到一份從未被掃描的位元組（覆審以並發寫入實測重現）。已改為**單次串流走訪**，同一次讀取同時餵給 SHA-256 與掃描器，掃描結果因此必定描述 digest 涵蓋的同一批位元組。順帶把每檔的三次讀取降為一次。
3. **整檔載入導致 `MemoryError`（真缺陷）**：`read_bytes()` + `decode()` 約需 2.1 倍檔案大小的記憶體，而 CLI 只攔 `OSError`／`BundleError`，大檔會以未處理例外與 exit 1 結束，違反既有的 `error: …`／exit 2 契約。改為 1 MiB 串流搭配 incremental decoder（跨 chunk 邊界的多位元組字元由解碼器正確處理，已補測試），並把 `MemoryError` 納入攔截。
4. **`--as-of` 測試只覆蓋一半（真缺陷）**：原測試中沒有任何記錄設過 `expires_at`，因此到期比較根本沒被執行——把 `--as-of` 改成完全忽略，測試仍全綠。已補到期邊界測試，並實際做**變異測試**確認：把 `now = parse_expiry(as_of) …` 改為忽略參數後，該測試如預期失敗。過程中另發現一件事實並修正文件：**核准 digest 涵蓋 `expires_at`**，所以到期時間必須在核准前寫在候選上，核准後才加會使該筆記錄驗證失敗。
5. **`first_observed` 語意宣稱過強（文件不實）**：當所選證據沒有時間戳時，`add-candidate` 會以候選建立時刻回填，兩個欄位因此可能只是寫入時間而非觀察時間。已在 `profile-schema.md` 誠實記錄。
6. **`install.md` 宣稱過寬（文件不實）**：原文說掃描涵蓋「審查者看不到但模型讀得到的字元」，但 variation selector（U+FE00–FE0F、U+E0100–E01EF）等並不在類別內，覆審實測可通過。已改為明確列出本專案拒絕的類別，並聲明它不是完整清單、逐檔審查仍然必要。是否擴大類別牽動四個檔案的一致性測試，列入下週佇列而非本週倉促變更。
7. **檔首 BOM 被當成攻擊（判斷題）**：以 `utf-8-sig` 存檔的 Windows 檔案會讓整個 bundle 被拒，訊息看起來像資安發現。專案他處（`distill_workflow._load_manifest`、`privacy_guard.scan_path`）本就容忍 BOM。已改為**放行檔首 BOM、仍拒絕檔案中間的同一字元**，並補測試與文件。

覆審同時確認以下宣稱屬實，未做更動：`--as-of` 確實只影響到期；到期為排他；確實沒有任何指令設定 `expires_at`；supersession 確實發生在核准的同一次寫入；README 疑難排解引用的 exit code 與訊息字串全部正確；`prepare_review_pack.py` 被阻擋時確實不產生任何檔案；本次 diff 未違反任何核心原則。
