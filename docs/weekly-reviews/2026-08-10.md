### 方向 B — 競品與類似工具（memory / personalization）

- Zylos Research《Memory Privacy and Retention for Persistent AI Agents》（2026-04-28）：主張把記憶當作「有治理的營運資料」而非無限期儲存——不同記憶類別應有不同存續期（使用者偏好長存且可編輯；作業狀態短 TTL），並列出使用者應有的四種控制：檢視、來源（provenance）、**到期可見性（"When will it expire?"）**、刪除權。此文直接佐證本週改動（`--expires-at`）：時間界定的偏好是主流治理文獻明確要求的能力，而本 repo 在此之前只有 schema 支援、沒有指令入口。
  - 來源：https://zylos.ai/research/2026-04-28-memory-privacy-retention-persistent-ai-agents/

## 4. 本週實際改動與驗收

### 改動:`add-candidate` 新增 `--expires-at`(單一主項)

上週查證確認的缺口:compile 支援 `expires_at`、驗證器接受它,但沒有任何指令會設定它——需要時限的偏好只能用 `temporary` scope 勉強替代,或手改 JSON(而手改核准後的記錄會被 digest 驗證擋下)。本週依既定設計把旗標加在**候選階段**:

- `profile_tool.py`:
  - `add_candidate_from_evidence` 新增 keyword `expires_at`(預設 `None`,行為完全不變)。
  - 設定時的三道檢查:(1) 必須是可解析的 ISO-8601;(2) **必須在未來**——已過期的候選永遠不會被編譯,核准它只會浪費一次 digest-bound 審查,故在建立時就拒絕;(3) 儲存前**正規化為 UTC(`Z` 結尾)**,使核准 digest 不受輸入時區寫法(`+09:00` vs `Z`)影響。
  - CLI 加 `--expires-at`(附 help 文字),傳入函式。
  - **digest 無需任何改動**:`candidate_digest` 的 approval subject 本來就涵蓋 `expires_at`,故「使用者核准的到期時間就是生效的到期時間」自動成立。
- 文件同步(三處,見方向 D):
  - `references/profile-schema.md`:staleness 段落改寫——說明旗標用法、UTC 正規化理由、拒絕過去時間的理由,並給出「時間界定用 `expires_at`、情境界定用 `temporary` scope,兩者可並用」的選擇準則。
  - `SKILL.md` 第 5 節:add-candidate 說明補一句 `--expires-at` 的用途與「必須在候選階段設定」的原因。
  - `CHANGELOG.md`:0.3.0「新增」加一條;「已知限制」刪除「沒有任何指令會設定它」一條(已不成立)。
- **未改動**:schema 版本(1.1,欄位本來就存在)、digest 演算法、approve/compile 行為、核心原則一律未動。

### 測試(基準線 120 → 121,另擴充一支既有測試)

1. 新增 `test_add_candidate_expiry_is_normalized_covered_by_digest_and_must_be_future`(test_scripts.py):`+09:00` 輸入 → 儲存為 `Z`;有/無 expiry 的 digest 不同;`not-a-timestamp` 與過去時間 → `ProfileError`。
2. 既有 lifecycle 測試(test_profile_lifecycle.py)升級:原本以「手改候選 JSON」模擬 expiry 的段落改為直接走 `add-candidate --expires-at` CLI,端到端驗證「設定 → digest 改變 → 核准 → 邊界前編譯得到 → 到期瞬間(exclusive)編譯不到」;另補 CLI 層的過期時間拒絕(exit code 2、不產生輸出檔)。無 expiry 時寫 `null` 的既有斷言保留。
