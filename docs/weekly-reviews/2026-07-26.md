### 方向 B — 競品與類似工具（memory / personalization）

### 方向 C — 安全與隱私強化（**本週改動來源**）

- Snyk《ToxicSkills》大規模掃描 3,984 個 agent skill：**36.82% 至少含一項安全缺陷**，確認的惡意 skill 中 **91% 使用 prompt injection**、100% 含惡意程式碼樣式；共確認 76 個惡意 payload。攻擊手法包含外部惡意程式下載、base64 混淆的憑證外流、以及停用安全機制／DAN 式 jailbreak。
  - 來源：https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub/
- Cloud Security Alliance 研究筆記《Agent Context Poisoning: SKILL.md and the New AI Supply Chain Attack Surface》 — 直接命中本 repo 的缺口。核心論點：agent 把 context 檔案當成可信指令，語意層無法區分開發者指令與第三方 skill 指令。列出的具體手法之一是 **不可見 Unicode Tag 字元（U+E0000–U+E007F）**：在「視覺上乾淨」的檔案中夾帶敵對指令，多數文字編輯器不顯示，但語言模型會讀取。建議控制項包含 hash 完整性驗證、來源控管、最小權限、審查閘門，以及 **「在內容進入模型 context 前，剝除或標記不可見字元」**。
  - 來源：https://labs.cloudsecurityalliance.org/research/briefing-csa-research-note-skill-md-agent-context-poisoning/ 、https://labs.cloudsecurityalliance.org/research/csa-research-note-skill-md-agent-context-poisoning-20260506/
- 供應鏈完整性驗證的同向研究（Palo Alto Unit 42《Trust No Skill》）主張把 skill 當成需要完整性驗證的一等供應鏈資產。本 repo 的 canonical bundle digest 與 full-SHA pinning 已符合此建議。
  - 來源：https://unit42.paloaltonetworks.com/ai-agent-supply-chain-risks/

**對照 repo 現況所發現的實際缺陷（本週修補）：**

全 repo 搜尋 `unicodedata` / `200B` / `E0000` / `202E` / bidi / 不可見字元相關處理，結果為**零命中**（僅 `profile_tool.py` 對 rule 欄位檢查控制字元）。`normalize_sessions.normalize_record()` 對不受信任的 transcript 只做 `text.replace("\x00", "").strip()`。這造成三個具體、可驗證的問題：

1. **審查閘門被繞過**：使用者在 evidence 審查畫面上看不到的隱形指令，會原樣通過正規化、進入 `evidence.jsonl`，並在審查時進入模型 context。本 repo 全部安全性都建立在「使用者審查他所看到的內容」之上；使用者看不到的字元使這個前提失效。
2. **redaction 可被規避**：在 secret 中插入零寬字元（例如 `sk-` + U+200B + 其餘）可讓字串不再匹配 `SECRET_PATTERNS`，使憑證躲過遮蔽寫入 `normalized.jsonl`。
3. **本 repo 自身即供應鏈標的**：這是一個公開、供他人安裝的 Skill。既有的 bundle digest 只能保證「核准後的位元組沒被改動」，無法保證「核准前人類看到的就是全部內容」。若有 PR 夾帶隱形字元，現有 CI 不會發現。

## 4. 本週實際改動與驗收

### 改動 1：隱形字元 context poisoning 防禦（三層縱深）

**設計原則**：剝除「無正當純文字用途」的字元，但**保留有正字法用途者**。U+200C（ZWNJ）與 U+200D（ZWJ）為波斯語、阿拉伯語、印度系文字與 emoji 序列所必需，強行剝除會破壞正常內容，因此改為「保留但發出警告」。這條界線在三個檔案中以同一個字元類別表達，並以測試強制三者一致。

- `skills/user-model-distiller/scripts/normalize_sessions.py`（`VERSION` 0.3.0 → 0.4.0）
  - 新增 `DECEPTIVE_INVISIBLE_PATTERN`：Unicode Tag 區塊（U+E0000–U+E007F）、bidi embedding/override 控制（U+202A–U+202E）、bidi isolate 控制（U+2066–U+2069）、word joiner 與不可見數學運算子（U+2060–U+2064）、零寬空白（U+200B）、BOM（U+FEFF）、interlinear annotation（U+FFF9–U+FFFB）、soft hyphen（U+00AD）。
  - 新增 `CONTROL_CHARACTER_PATTERN`：tab／newline 以外的 C0/C1 控制字元（原本只移除 NUL）。
  - 新增 `sanitize_untrusted_text()`，並在 `normalize_record()` 中**於 redaction 之前**執行，同時把 `\r\n`／`\r` 正規化為 `\n`。順序是刻意的：先剝除才能避免隱形字元把 secret 切開躲過 `SECRET_PATTERNS`。
  - 移除數量計入既有的 `redaction_count`（**不新增欄位**）。原因：`privacy_guard.TOP_LEVEL_FIELDS` 是封閉集合，新增欄位會觸發 `unexpected_field` blocker，必須升 schema 版本並牽動 `prepare_review_pack` 與 fixtures — 本週刻意避開這種大範圍改動。另加 `MAX_REPORTED_REDACTIONS` 上限，避免病態輸入讓計數超出 gate 的合法範圍而反而使記錄失效。
- `skills/user-model-distiller/scripts/privacy_guard.py`（`VERSION` 0.3.0 → 0.4.0）
  - 新增 blocker `deceptive_invisible_characters`：內建正規化器不可能產生這些字元，因此已正規化檔案中若仍存在，即代表該檔案是手工產生或事後被改動 — 兩種模式皆阻擋。
  - 新增 warning `zero_width_joiner`：保留的 U+200C/U+200D 仍可能把 token 切開，故在 `local` 模式警告、在 `external-review` 模式（任何 warning 皆阻擋揭露）自動升級為阻擋。
- `tools/check_repository.py`
  - CI 守門新增：追蹤檔案不得含上述隱形／bidi 字元，錯誤訊息回報碼位與檔名（例：`invisible or bidi control character U+E0045 found: SKILL.md`）。非 UTF-8 檔案跳過此檢查而**不**新增錯誤類型，避免未來加入二進位資產時產生混淆的 CI 失敗（二進位仍由既有 NUL 檢查涵蓋）。
  - 此項防的是本 repo 自身：發佈中的 SKILL.md 就是他人的 agent context，隱形字元在此屬供應鏈缺陷。
- 文件同步：`references/security-and-privacy.md`（Memory-poisoning defenses 新增 3 條，含 ZWJ 保留理由）、`docs/threat-model.md`（信任邊界圖更新，新增 2 條威脅／控制列）、`SKILL.md` 第 3 節（說明會剝除哪些字元、計入 `redaction_count`、不得為了還原而把原始文字放回審查畫面）、`README.md` 中英文安全模型段落各補一段。
- 測試：新增 **12 項**
  - `tests/test_scripts.py` 4 項：剝除並正確計數、ZWJ/ZWNJ 與換行倖存、隱形字元無法把 secret 切開躲過遮蔽、全為隱形字元的訊息被丟棄。
  - `tests/test_privacy_guard.py` 2 項：隱形字元阻擋而 joiner 僅警告（含 external-review 升級）、**報告本身不得回吐隱形字元或原文**。
  - `tests/test_repository_guard.py`（新檔）6 項：乾淨樹通過、Tag 字元失敗、7 種 bidi/零寬字元失敗（subTests）、正字法 joiner 允許、非 UTF-8 不致當掉、**三個檔案的字元類別必須完全一致**（防止日後三層定義漂移）。
  - 測試檔內所有隱形字元一律以碼位（`chr()`）建構，不放字面字元 — 否則會（正確地）觸發本週新增的 CI 守門。撰寫過程中確實踩到這一點並修正，可視為守門有效的第一個實證。

**未改動**：核心原則、`profile.json` schema、記錄欄位集合、approval/digest 流程、CI/release workflow、既有 privacy gate 判定邏輯一律不動。
